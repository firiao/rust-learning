# Лекция 22. Ошибки в реальном проекте

**Время:** ~25 минут

**Нужно знать заранее:** `Result`, `?`, свой `enum` ошибок, `Display`, `Error` (лекция 10).

**Новые слова в этой лекции:**
- **`anyhow`** — крейт для приложений: «любая ошибка + контекст»;
- **контекст ошибки** — сообщение «что я пытался сделать», добавляемое к причине;
- **`thiserror`** — крейт для библиотек: генерация своего `enum` ошибок;
- **`bail!` / `ensure!`** — макросы `anyhow` для раннего возврата;
- **логирование** — запись событий программы (не путать с выводом результата).

---

## 1. Два мира ошибок

В лекции 10 мы писали свой `enum` ошибок руками: вариант, `Display`, `Error`. Это правильно для библиотеки, но в приложении превращается в много служебного кода.

Есть правило, которое стоит запомнить:

| Где | Инструмент | Почему |
|---|---|---|
| **Библиотека** | свой `enum` (+ `thiserror`) | вызывающий должен различать причины |
| **Приложение** | `anyhow` | всё равно печатать сообщение и выходить |

---

## 2. `thiserror` — библиотека

```bash
cargo add thiserror
```

Вместо ручного `impl Display` пишем атрибуты:

```rust
use thiserror::Error;

#[derive(Debug, Error)]
enum ParseError {
    #[error("пустая строка")]
    Empty,

    #[error("не число: {0:?}")]
    NotANumber(String),

    #[error("{value} вне диапазона {min}..={max}")]
    OutOfRange { value: i64, min: i64, max: i64 },
}
```

Разберём:

- `#[derive(Error)]` — генерирует `Display` и `impl std::error::Error`;
- `#[error("...")]` — текст сообщения; `{0:?}` — первое поле в отладочном виде, `{value}` — именованное поле.

То, что в лекции 10 занимало 20 строк, теперь 12 строк объявления. Логика та же.

### Вложенная ошибка (`#[from]`)

```rust
use thiserror::Error;

#[derive(Debug, Error)]
enum LoadError {
    #[error("не удалось прочитать файл {path}")]
    Io {
        path: String,
        #[source]
        source: std::io::Error,
    },

    #[error("неверный формат")]
    Parse(#[from] std::num::ParseIntError),
}
```

- `#[source]` — «причина»: исходная ошибка, которую можно показать цепочкой;
- `#[from]` — автоматически реализует `From<ParseIntError>`, поэтому `?` будет работать без `map_err`.

## 3. `anyhow` — приложение

```bash
cargo add anyhow
```

```rust
use anyhow::{Context, Result};

fn load_config(path: &str) -> Result<String> {
    let text = std::fs::read_to_string(path)
        .with_context(|| format!("не удалось прочитать {path}"))?;
    Ok(text)
}

fn main() -> Result<()> {
    let cfg = load_config("config.json")?;
    println!("{cfg}");
    Ok(())
}
```

Разберём:

- `anyhow::Result<T>` — это `Result<T, anyhow::Error>`; тип ошибки не пишется;
- `.with_context(|| "...")?` — добавить сообщение «что я пытался сделать». Если файла нет, вывод будет примерно такой:

```text
Error: не удалось прочитать config.json

Caused by:
    No such file or directory (os error 2)
```

Видно и **что** делали, и **почему** не вышло.

- `|| format!("...")` — замыкание (лекция 15), ленивое: сообщение построится, только если ошибка есть.

### `bail!` и `ensure!`

```rust
use anyhow::{bail, ensure, Result};

fn check_epochs(epochs: usize) -> Result<()> {
    ensure!(epochs > 0, "эпох должно быть больше нуля");
    if epochs > 1_000_000 {
        bail!("слишком много эпох: {epochs}");
    }
    Ok(())
}
```

- `ensure!(условие, "текст")` — если условие ложно, вернуть ошибку;
- `bail!("текст")` — вернуть ошибку сразу.

Оба — сокращение для `return Err(anyhow!("..."))`.

### Своя ошибка внутри `anyhow`

`anyhow` принимает любую ошибку, реализующую `Error`, включая твой `enum` из `thiserror`. Поэтому в приложении можно смешивать: внутри модуля — точный тип, наверху — `anyhow`.

## 4. Логирование

Печать в `stdout` — это **результат** программы. Диагностика должна идти в `stderr`.

```rust
fn main() {
    eprintln!("[debug] старт");            // в stderr
    println!("результат");                 // в stdout
}
```

Для настоящего проекта берут `tracing` или `log` + `env_logger`:

```rust
// Cargo.toml: tracing = "0.1"
use tracing::{info, warn};

fn main() {
    tracing_subscriber::fmt::init();       // настройка вывода
    info!("старт обработки");
    warn!("пустой входной файл");
}
```

Пока достаточно понимать разницу:

| Куда | Что |
|---|---|
| `stdout` | данные (то, что можно перенаправить в файл) |
| `stderr` | диагностика, прогресс, ошибки |
| `dbg!` | быстрая отладка во время разработки (lecture 19) |

## 5. Правило выбора

```text
ты пишешь библиотеку?      → thiserror (или свой enum руками)
ты пишешь приложение?      → anyhow
внутри библиотеки детали?  → конкретные типы, не anyhow
на границе приложения?     → anyhow + context
```

Почему `anyhow` не для библиотек: он стирает тип ошибки, и вызывающий не сможет отличить «нет файла» от «неверный формат».

## 6. Типичные ошибки

### `anyhow` в публичном API библиотеки

```text
error[E0446]: private type `...` in public interface
```

Или просто неудобный API. Для библиотек — свой тип.

### Забыли `#[source]`

Цепочка причин пропадёт: будет видно только внешнее сообщение.

### `?` без `From`

```text
error[E0277]: `?` couldn't convert the error to `MyError`
```

Решение: `#[from]` в `thiserror` или `.map_err(...)`.

## 7. Что ты теперь знаешь

- Библиотека — свой `enum` ошибок (`thiserror`), приложение — `anyhow`.
- `thiserror`: `#[derive(Error)]`, `#[error("...")]`, `#[from]`, `#[source]`.
- `anyhow`: `Result<T>`, `.context()`, `bail!`, `ensure!`.
- Контекст показывает, что делали и почему не вышло.
- Диагностика — в `stderr`, данные — в `stdout`.
- `tracing`/`log` — для настоящего логирования.
