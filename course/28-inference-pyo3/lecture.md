## 1. Зачем Rust в инференсе

Обучение почти всегда на Python: там данные, PyTorch, ноутбуки. А вот **запуск** модели в продакшене — другая задача:

| Требование | Python | Rust |
|---|---|---|
| Развернуть одной командой | нужен интерпретатор и зависимости | один бинарник |
| Память | 300+ МБ на процесс | десятки МБ |
| Холодный старт | секунды | миллисекунды |
| Предсказуемость задержек | GC и GIL | нет GC, нет GIL |

Отсюда типичный пайплайн: **обучили в PyTorch → экспортировали в ONNX → обслужили на Rust**.

ONNX — это «нейтральный» формат: его понимают и PyTorch, и наш `ort`, и сама Python-экосистема.

## 2. Экспорт модели (на стороне Python)

```python
import torch

model = ...            # твоя обученная модель
dummy = torch.randn(1, 3, 224, 224)

torch.onnx.export(
    model, dummy, "model.onnx",
    input_names=["input"], output_names=["output"],
)
```

Получается файл `model.onnx` с графом и весами. Его и будет читать Rust.

Важно: **вход должен иметь фиксированную форму**. Если модель ждёт `1×3×224×224`, Rust обязан подать ровно это.

## 3. Инференс с `ort`

```toml
# Cargo.toml
[dependencies]
ort = "2.0.0-rc.15"
ndarray = "0.17"
```

Каркас (сверься с docs.rs — API меняется):

```rust
use ndarray::{Array4, ArrayViewD};
use ort::session::Session;

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let mut session = Session::builder()?.commit_from_file("model.onnx")?;

    // форма 1×3×224×224, данные в Vec<f32>
    let input = Array4::<f32>::zeros((1, 3, 224, 224));

    let outputs = session.run(ort::inputs![input.view()]?)?;

    // первый выход: узнаём форму из модели
    let output: ArrayViewD<f32> = outputs[0].try_extract_array()?;
    println!("форма выхода: {:?}", output.shape());

    // argmax по всем значениям
    let (best_index, best_score) = output
        .iter()
        .enumerate()
        .max_by(|a, b| a.1.partial_cmp(b.1).unwrap())
        .unwrap();

    println!("класс {best_index}, уверенность {best_score:.4}");
    Ok(())
}
```

Разберём то, что **верно независимо от версии крейта**:

- `Session::builder()?...commit_from_file(...)` — загрузить модель; ошибка, если файла нет или формат не понят;
- `ort::inputs![...]` — макрос подготовки входов по имени (те самые `input_names` из экспорта);
- выход — `ArrayViewD<f32>`: N-мерный вид на данные `ndarray` (лекция 25);
- предсказание — `argmax`: индекс наибольшего значения. `max_by` с `partial_cmp` и `unwrap` здесь допустим, потому что значения модели не `NaN`; в общем случае надо обрабатывать `None`.
- `output.iter().enumerate()` — пары `(индекс, значение)` из итератора (лекция 14).

Что проверять при первом запуске:

1. имена входов/выходов — `session.inputs` (в разных версиях по-разному);
2. форму входа — модель скажет, что ждёт;
3. масштаб данных — нормализация (см. ниже).

## 4. Самое частое место ошибок: препроцессинг

Модель ждёт не «картинку», а тензор `1×3×224×224` из `f32` со средними и дисперсиями, как при обучении.

```rust
/// Нормализация как в ImageNet: (x/255 - mean) / std
fn normalize(pixels: &[u8], mean: [f32; 3], std: [f32; 3]) -> Vec<f32> {
    let mut out = Vec::with_capacity(pixels.len());
    for (i, &p) in pixels.iter().enumerate() {
        let channel = i % 3;
        let v = p as f32 / 255.0;
        out.push((v - mean[channel]) / std[channel]);
    }
    out
}
```

Правило: **препроцессинг на Rust должен побитово повторять препроцессинг на Python**. Если в питоне было `ToTensor() + Normalize(mean, std)`, а в Rust забыли `/255`, модель выдаст мусор, и ты будешь искать баг в модели.

Проверка: прогони одно и то же изображение в PyTorch и в Rust и сравни выходы. Расхождение должно быть в пределах `1e-5`.

## 5. Python-расширение на `pyo3`

Другая стратегия: не переносить инференс целиком, а ускорить **узкое место** Python-кода.

```toml
# Cargo.toml
[lib]
name = "fast_ops"
crate-type = ["cdylib"]

[dependencies]
pyo3 = { version = "0.23", features = ["extension-module"] }
```

```rust
use pyo3::prelude::*;

/// Сумма квадратов: то же, что sum(x*x for x in values)
#[pyfunction]
fn sum_of_squares(values: Vec<f64>) -> f64 {
    values.iter().map(|x| x * x).sum()
}

#[pymodule]
fn fast_ops(m: &Bound<'_, PyModule>) -> PyResult<()> {
    m.add_function(wrap_pyfunction!(sum_of_squares, m)?)?;
    Ok(())
}
```

Разберём:

- `crate-type = ["cdylib"]` — собрать динамическую библиотеку, которую загрузит Python;
- `#[pyfunction]` — превратить функцию в вызываемую из Python (это процедурный макрос, лекция 11);
- `#[pymodule]` — точка входа модуля; регистрируем функции;
- `Vec<f64>` в параметрах — `pyo3` сам конвертирует список Python в `Vec`.

Сборка:

```bash
pip install maturin
maturin develop --release   # собрать и установить в текущее окружение
```

Использование:

```python
import fast_ops

print(fast_ops.sum_of_squares([1.0, 2.0, 3.0]))   # 14.0
```

Замер «до/после» — обязательная часть работы:

```python
import time
import fast_ops

data = [float(i) for i in range(1_000_000)]

t0 = time.perf_counter()
sum(x * x for x in data)
print("python:", time.perf_counter() - t0)

t0 = time.perf_counter()
fast_ops.sum_of_squares(data)
print("rust:", time.perf_counter() - t0)
```

## 6. Капстоун: что сдать

Один из двух вариантов (или оба, если хочешь):

**Вариант А — сервис инференса.**
CLI на Rust: читает `model.onnx`, принимает данные (файл или stdin в JSON), выдаёт предсказание в JSON. Требования: `clap` для аргументов, `serde` для ввода-вывода, `ort` для модели, тесты на препроцессинг, числа совпадают с PyTorch в пределах `1e-5`.

**Вариант Б — ускорение Python-кода.**
Берёшь свой реальный Python-скрипт, находишь узкое место, переносишь на Rust через `pyo3`, замеряешь «до/после» и пишешь отчёт: что ускорилось, во сколько раз, чем заплатил (сборка, зависимости, сложность).

В обоих случаях сдаётся: код + README с замерами + объяснение, почему выбрал именно этот способ.
